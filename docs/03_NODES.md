# ۳. nodeها: سرورهای پروکسی

## پروتکل‌ها
| پروتکل | چرا | نکته |
|---|---|---|
| **VLESS + Reality + XTLS-Vision** (Xray-core) | در برابر فیلترینگ ایران مقاوم‌ترین گزینه‌ی TCP است. دامنه و گواهی لازم ندارد؛ به شکل TLS یک سایت خارجی واقعی درمیآید. | کلید Reality برای هر node جداست. SNI و dest از یک فهرست سایت‌های سالم چرخشی انتخاب میشوند. |
| **MTProto با fake-TLS و ad tag** | برای تلگرام یک‌کلیکی است و **کانال اسپانسر** دارد (`02_GROWTH.md`). | سرور پروکسی باید ad tag و fake-TLS را با هم داشته باشد. انتخاب در فاز ۲. |
| Hysteria2 (QUIC) | اختیاری است. وقتی UDP باز باشد، سریع است. | در ایران UDP زیاد محدود میشود. فقط اگر سنجش نشان داد کار میکند. |
| مسیر CDN (WS یا gRPC پشت Cloudflare) | پشتیبان برای وقتی که IP مستقیم سوخته است. | توکن و دامنه‌ی Cloudflare میخواهد. فعلاً بیرون از دامنه است، چون D2 فقط توکن هتزنر است. |

## چرخه‌ی عمر node
```
requested → creating → booting → registering → ready → (draining) → retiring → deleted
                                         ↘ unhealthy → repairing ↗ / → retiring
```
1. **requested:** چرخه‌ی `fleet` تصمیم میگیرد node لازم است. بودجه و سقف تعداد را **پیش از** ساخت میسنجد.
2. **creating:** سرور از راه API هتزنر ساخته میشود، با:
   - **برچسب‌ها:** `managed-by=proxy-hub`، `role=node` و `node-id=<uuid>`.
   - **فایروال هتزنر** همین سیستم.
   - **snapshot آماده** (بخش بعد).
   - **cloud-init** با یک توکن ثبت یک‌بارمصرف.
3. **registering:** عامل node بالا میآید، با توکن یک‌بارمصرف گواهی mTLS میگیرد و کلید Reality میسازد. کلید عمومی را میفرستد و کلید خصوصی هرگز از node بیرون نمیرود.
4. **ready:** چرخه‌ی `configs` روی آن کانفیگ میسازد.
5. **unhealthy:** heartbeat نیامده است. به ترتیب: restart سرویس از راه عامل، بعد reboot از راه API هتزنر، بعد تعویض.
6. **burned (سوخته از ایران):**
   - کانفیگ تازه روی آن ساخته نمیشود.
   - پست‌هایش 🚫 میگیرند.
   - وقتی دیگر کانفیگ فعالی روی آن نیست، یا حداکثر بعد از N ساعت، **retiring** میشود.
7. **deleted:** حذف فقط اگر **هم** برچسب `managed-by=proxy-hub` **هم** ردیف در دیتابیس با همان `hetzner_id` باشد (قانون ۵ در `CLAUDE.md`).

## image آماده (snapshot) برای بالا آمدن سریع
- **چه چیزی ساخته میشود:** با **Packer** و پلاگین `hcloud` یک snapshot از Ubuntu LTS ساخته میشود، با:
  - Xray، پروکسی MTProto، عامل node، nftables و تنظیمات کرنل (BBR و ...)، همه **با نسخه و hash ثابت**.
- **فایده:** هر node تازه به‌جای چند دقیقه نصب، در کمتر از یک دقیقه آماده است.
- **به‌روزرسانی:** snapshot در فاز ۶ خودکار هر ماه دوباره ساخته میشود. nodeهای قدیمی به‌مرور (rolling) با node تازه عوض میشوند و هرگز درجا به‌روز نمیشوند.

## سنجش «سوخته از ایران» (چرخه‌ی `reachability`)
سه منبع، با وزن:
1. **probe داخل ایران (قوی‌ترین):** TCP، دست‌دادن TLS و یک اتصال واقعی VLESS و MTProto. اگر چند بار پشت هم از چند نقطه شکست بخورد، سوخته است.
2. **نشانه‌ی ترافیک (بدون probe):**
   - **وقتی یعنی سوخته:** تعداد اتصال یک node ناگهان به نزدیک صفر میرسد، در حالی که nodeهای دیگر عادی‌اند و خود node سالم است.
   - **یک مزیت:** این روش هیچ داده‌ای از کاربر نمیخواهد؛ فقط تعداد کلی.
3. **سرویس عمومی سنجش با نقطه‌ی ایران:** پشتیبان است و دقتش کمتر است.

حکم سوختگی با چند منبع گرفته میشود تا یک خطای شبکه باعث تعویض بی‌دلیل نشود.

## چرخش IP
- **راه ساده:** IP سوخته با حذف node میرود و node تازه IP تازه میگیرد.
- **راه ارزان‌تر:** در هتزنر میشود **Primary IP** را از سرور جدا کرد، حذف کرد و یکی تازه گرفت. پس شاید بدون حذف سرور هم بشود IP را عوض کرد. این در فاز ۴ سنجیده میشود (هزینه و زمان کدام بهتر است).
- **مناطق:** چند منطقه (fsn1، nbg1، hel1). رنج IP منطقه‌ها فرق دارد و فیلترینگ معمولاً رنج‌به‌رنج است.

## جلوگیری از abuse روی node (بخشی از image)
- **بستن پورت ایمیل:** خروجی 25، 465 و 587 بسته است، تا از پروکسی اسپم فرستاده نشود.
- **بستن تورنت:** در routing Xray با sniffing `bittorrent` بسته میشود.
- **بستن شبکه‌های خصوصی:** خروجی به رنج‌های خصوصی و metadata (`169.254.169.254`) بسته است.
- **سقف حجم و زمان هر کانفیگ:** با StatsService سنجیده و اعمال میشود.
- **لاگ:** access log در Xray و پروکسی MTProto **خاموش** است (قانون ۷).
