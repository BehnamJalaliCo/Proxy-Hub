# ۶. اداره‌ی خودکار، امنیت و ایمنی

## خودترمیمی: چه کسی چه چیزی را درست میکند
| خرابی | چه کسی میفهمد | چه میکند |
|---|---|---|
| یک سرویس داخل node افتاد | عامل node | restart. اگر سه بار شد، گزارش «بیمار» |
| node جواب نمیدهد | `node_health` (heartbeat نیامد) | reboot از API هتزنر؛ اگر نشد، تعویض |
| IP از ایران بسته شد | `reachability` | node تازه، 🚫 روی پست‌ها، retire node قدیمی |
| کانفیگ به سقف رسید | عامل و `post_status` | کاربر Xray حذف، 🔴 یا ⌛️ روی پست |
| تلگرام 429 داد | ناشر | صبر به اندازه‌ی `retry_after`، ادامه از صف |
| API هتزنر خطا داد یا شلوغ بود | چرخه‌ها | تلاش دوباره با فاصله‌ی رو‌به‌افزایش (backoff)؛ هیچ کار نیمه‌تمامی نمیماند، چون چرخه دوباره میسنجد |
| یکی از کانتینرهای پنل افتاد | Docker healthcheck | restart خودکار |
| کل سرور پنل افتاد | نگهبان بیرونی | هشدار به مالک. nodeها با آخرین کانفیگ خود به کار ادامه میدهند؛ فقط پست تازه نمیآید. |
| دیسک پنل پر میشود | `self` | پاک کردن لاگ و image قدیمی؛ هشدار پیش از ۸۵٪ |

## هشدار به مالک: فقط وقتی کد نمیتواند حل کند
- بودجه‌ی ماه به ۸۰٪ رسید، یا سقف تعداد node مانع کار است.
- هیچ node سالمی نیست، یا بیشتر از X٪ nodeها در یک ساعت سوختند (شاید فیلترینگ گسترده است).
- پنل یا نگهبان بیرونی مشکل دارند.
- **abuse یا هشدار از طرف هتزنر** (پایین).
- توکن تلگرام یا هتزنر کار نمیکند (شاید باطل شده است).

## سقف‌ها و کلید توقف
- **سقف بودجه‌ی ماهانه و سقف تعداد node:** پیش از هر ساخت سنجیده میشوند. کد هیچ راهی برای رد شدن از آن‌ها ندارد.
- **سقف سرعت ساخت:** مثلاً حداکثر N node در ساعت. اگر حلقه‌ای پیش بیاید، خرج انفجاری نمیشود.
- **کلید توقف (kill switch) در پنل:** همه‌ی چرخه‌ها متوقف میشوند. nodeها روشن میمانند و پست تازه نمیآید. هیچ چیز حذف نمیشود.

## abuse هتزنر: تنها جای نیمه‌دستی
- **مشکل:** هتزنر گزارش abuse را با **ایمیل** به صاحب حساب میفرستد و جواب میخواهد. اگر جواب نیاید، ممکن است IP یا سرور قفل شود. این بخش API عمومی ندارد.
- **طرح خودکار:**
  1. پنل صندوق ایمیل حساب هتزنر را با IMAP میخواند (فقط خواندن). اجازه‌اش با مالک است.
  2. گزارش abuse را تشخیص میدهد و node مربوط را **فوراً retire میکند**: IP میرود و کانفیگ‌ها روی node تازه.
  3. یک متن پاسخ آماده میکند و به مالک هشدار میدهد. فرستادن پاسخ در کنسول هتزنر ممکن است کار مالک باشد، مگر اینکه راه خودکار مطمئنی پیدا شود (فاز ۶).
- **پیشگیری:** بستن ایمیل، تورنت و رنج‌های خصوصی، سقف حجم هر کانفیگ. این‌ها گزارش abuse را خیلی کم میکنند.

## امنیت
- **توکن هتزنر فقط مال project جدا است.** پنل در شروع کار فهرست سرورهای project را میخواند. اگر سروری بی برچسب `managed-by=proxy-hub` دید، به‌جز سرور خود پنل، **چرخه‌ی `fleet` روشن نمیشود** و هشدار میدهد.
- **حذف دوقفله:** برچسب درست **و** ردیف دیتابیس با همان `hetzner_id`. یک آزمون این را همیشه میسنجد.
- **سرور پنل:**
  - SSH فقط با کلید، روی یک پورت غیرپیش‌فرض.
  - فایروال هتزنر: فقط 443 و پورت SSH.
  - داشبورد پشت ورود امن (passkey یا رمز قوی همراه 2FA).
- **nodeها:**
  - SSH بسته است. node فقط از راه عامل و mTLS اداره میشود.
  - هر چیزی که لازم شد، با تعویض node حل میشود، نه با ورود به آن.
- **کلید Reality:** روی خود node ساخته میشود و بیرون نمیرود.
- **رمزها:** هرگز در ریپو، لاگ یا چت. CI gitleaks دارد.

## حریم کاربر (قانون ۷)
- **لاگ:** Xray با `loglevel: none` (یا warning بدون access log) اجرا میشود. پروکسی MTProto هم بی لاگ اتصال است.
- **چه ذخیره میشود:** عامل فقط عددهای کلی میفرستد: مصرف هر کانفیگ، تعداد اتصال و منابع سرور.
- **CRM:** فقط از رویدادهای خود تلگرام (عضویت و ترک کانال) ساخته میشود.

## backup و بازگردانی
- **روزانه:** `pg_dump` و restic، رمزنگاری‌شده، به Object Storage یا Storage Box هتزنر.
- **هفتگی:** آزمون خودکار بازگردانی در یک Postgres موقت.
- **از دست رفتن کل پنل:**
  1. سرور تازه.
  2. بازگردانی دیتابیس.
  3. nodeها خودشان دوباره وصل میشوند، چون گواهی mTLS و آدرس پنل را دارند. آدرس پنل باید **دامنه** باشد، نه IP، تا با سرور تازه عوض نشود. پس یک دامنه برای پنل لازم است (فاز ۰).
