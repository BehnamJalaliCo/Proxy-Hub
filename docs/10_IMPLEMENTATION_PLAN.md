# ۱۰. پلن اجرایی (وارسی‌شده)

> **تاریخ:** ۲۰۲۶-۱۱-۰۲. این سند جای «پیشنهاد» و «باید سنجیده شود» در سندهای ۰۰ تا ۰۹ را با **واقعیت وارسی‌شده** پر میکند و کار را به گام‌های قابل ساخت و قابل آزمون میشکند.
> **قانون این سند:** هر ادعای فنی یا (۱) با خواندن **سورس همان نسخه** یا **نصب و بررسی خود کتابخانه** وارسی شده، یا (۲) منبع رسمی دارد، یا (۳) صریحاً «**فقط با آزمایش میدانی معلوم میشود**» خورده و آزمایشش تعریف شده است. حدس در این سند نیست.
> **وضعیت:** هنوز هیچ کدی نوشته نشده و هیچ سروری ساخته نشده است. تصمیم‌های باز (بخش ۸) با مالک است.

## ۲. چه چیزی در طرح قبلی عوض میشود
1. **هزینه:** هر node حدود ۶٫۵ یورو است، نه ۳. جدول واقعی در بخش ۷ است.
2. **MTProto:** mtg کنار رفت؛ telemt اضافه شد. ad tag یعنی IP کاربر به تلگرام میرسد (M1). تنظیم ضد لاگ هر نامزد مشخص و در CI قفل است.
3. **سنجش ایران (O5):** اول Globalping (شبکه‌های خانگی و موبایل) و check-host، به‌همراه نشانه‌ی ترافیک؛ VPS ایرانی فقط اختیاری.
4. **چرخش پیش‌دستانه‌ی IP** (تازه) و **ترمز سوختن گسترده** (سخت‌گیرانه‌تر از قبل).
5. **abuse:** پرچم `blocked` هتزنر از فاز ۲ پایش میشود (قبلاً فقط IMAP در فاز ۶ بود).
6. **ساده‌سازی ابزارها** (Redis، Packer و Prometheus/Grafana/Loki نیست): پیشنهاد N4 که نیاز به تأیید دارد.
7. **DNS و backup با همان توکن هتزنر** (D2 کامل‌تر میشود).
8. **ماه اول سقف تعداد سرور کم است** (H7).

```
├─ node-image/            اسکریپت ساخت image + versions.lock (آدرس + sha256 هر جزء)
├─ deploy/                docker-compose.yml، Caddyfile، cloud-init پنل، deployer (GitOps)، backup
└─ .github/workflows/     ci.yml
```

### ۳.۲ اجزای در حال اجرا روی سرور پنل (Docker Compose)
| کانتینر | کار | نکته |
|---|---|---|
| `caddy` | HTTPS خودکار. `panel.<domain>` برای داشبورد و webhook تلگرام؛ `agent.<domain>` برای عامل‌ها با **mTLS اجباری** (`client_auth require_and_verify`) | فقط 80 و 443 باز |
| `api` | FastAPI: داشبورد، webhook، API عامل | webhook فقط ذخیره میکند و فوراً 200 میدهد |
| `worker` | همه‌ی چرخه‌های کنترل، هر کدام یک task در asyncio با **قفل advisory در Postgres** | دو worker هم‌زمان یک کار را دوبار نمیکنند |
| `postgres` | منبع حقیقت، و صف (`outbox` با `FOR UPDATE SKIP LOCKED`) | backup روزانه |
| `checker` | یک کلاینت Xray برای **سنجش واقعی هر کانفیگ پیش از پست**: با همان کانفیگ از پنل به node وصل میشود و یک آدرس آزمون را از داخل تونل باز میکند | فاز ۲ |

**اندازه‌ی سرور پنل (O2):** با ابزارهای ساده‌شده (N4)، این‌ها در **CPX12 (۲GB، ۱۱٫۹۹ یورو)** جا میشوند. بدون N4، یا برای فضای بیشتر، **CPX22 (۴GB، ۱۹٫۹۹ یورو)** لازم است. بزرگ کردن بعدی با API شدنی است (`change_type`)، ولی چند دقیقه پنل را خاموش میکند.

> **ساده‌سازی پیشنهادی نسبت به سند ۰۵ (نیاز به تأیید مالک، N4):** Redis، Packer و پشته‌ی Prometheus/Grafana/Loki در نسخه‌ی اول **نیست**. دلیل: قفل با advisory lock خود Postgres، صف با جدول `outbox`، سقف نرخ تلگرام در همان یک ناشری که قفل را دارد، و ساخت image با خود API هتزنر (`servers.create_image`، وارسی‌شده) انجام میشود. هر جزء کمتر یعنی یک چیز کمتر برای خراب شدن، backup و نگهداری. اگر عدد واقعی نشان داد لازم است، اضافه میشوند.

### ۳.۳ قفل‌های ایمنی (قلب سیستم؛ قانون‌های ۴، ۵ و ۸)
همه‌ی کارهای «خطرناک» هتزنر (ساخت، حذف، rebuild) فقط از یک ماژول (`safety/`) میگذرند. یک **تست معماری** در CI شکست میخورد اگر جای دیگری از کد متد ساخت یا حذف adapter را صدا بزند.

**`can_create(...)` فقط وقتی «بله» میدهد که همه‌ی این‌ها درست باشد:**
1. کلید توقف (kill switch) خاموش است.
2. سقف بودجه‌ی ماه **و** سقف تعداد node در تنظیمات **تعریف شده‌اند** (پیش‌فرض ندارند؛ نبودشان = «نه»).
3. `تعداد node زنده + در حال ساخت + ۱ ≤ سقف تعداد`.
4. `خرج پیش‌بینی‌شده‌ی ماه + هزینه‌ی node تازه تا پایان ماه ≤ سقف بودجه` — قیمت‌ها **زنده از API هتزنر** خوانده میشوند، نه عدد ثابت در کد.
5. تعداد ساخت در ۶۰ دقیقه‌ی گذشته کمتر از سقف سرعت ساخت است.
6. نگهبان شروع (startup guard) سبز است.

**`can_delete(server, row)` فقط وقتی «بله» میدهد که همه‌ی این‌ها درست باشد:**
1. برچسب `managed-by=proxy-hub` روی خود سرور در هتزنر هست.
2. برچسب `role` یکی از `node` یا `builder` است (سرور پنل `role=panel` دارد و **delete protection** خود هتزنر هم رویش روشن است).
3. ردیفی در دیتابیس با **همان `hetzner_id`** هست و وضعیتش `retiring` است.
4. delete protection روی سرور خاموش است.

**نگهبان شروع:** worker در شروع **همه‌ی** سرورهای project را (بی فیلتر برچسب) میخواند. اگر حتی یک سرور بی برچسب `managed-by=proxy-hub` دید، چرخه‌ی `fleet` روشن نمیشود و به مالک هشدار میدهد (قانون ۴ در `CLAUDE.md`).

**آزمون‌ها:** جدا از تست‌های معمولی، **تست خاصیت‌محور** (Hypothesis): هزاران ترکیب تصادفی از برچسب، ردیف دیتابیس و وضعیت ساخته میشود و ثابت میشود `can_delete` فقط وقتی «بله» میدهد که هر دو شرط قانون ۵ با هم برقرار باشد، و `can_create` هرگز از سقف رد نمیشود (قانون ۸).

### ۳.۴ چرخه‌ی کنترل: الگوی مشترک و مقاومت در برابر افتادن وسط کار
- هر چرخه هر چند ثانیه: قفل advisory میگیرد ← حالت مطلوب را از دیتابیس میخواند ← حالت واقعی را میسنجد ← **یک** کار کوچک ← نتیجه در `node_events` و `actions_log`.
- **کلید یکتایی هر ساخت:** پیش از صدا زدن API، ردیف node با `node_id` تازه و وضعیت `requested` نوشته میشود و سرور با برچسب `node-id=<node_id>` ساخته میشود. اگر پنل درست بین «درخواست ساخت» و «ثبت نتیجه» بیفتد، بار بعد با `label_selector=node-id=...` همان سرور پیدا میشود و **دوباره ساخته نمیشود**. این همان آزمون آشوب فاز ۱ است.
- **حالت خشک (dry-run):** adapter واقعی با یک «ضبط‌کننده» عوض میشود که فقط مینویسد «این کار را میکردم». داشبورد همین فهرست را نشان میدهد.
- **چرخه‌ی عمر node** یک جدول گذارهای مجاز دارد (همان نمودار `03_NODES.md`) و هر گذار غیرمجاز در تست شکست میخورد.

### ۳.۶ کانال تلگرام
- **webhook:** `setWebhook` با `secret_token` (سرآیند `X-Telegram-Bot-Api-Secret-Token` بررسی میشود) و `allowed_updates` که صریحاً `chat_member` را دارد. هر update با `update_id` یکتا ذخیره میشود (`ON CONFLICT DO NOTHING`)، پس تکرار تلگرام چیزی را دوبار نمیشمارد.
- **صف ارسال (`outbox`):** پست، ویرایش وضعیت، ساخت لینک دعوت و هشدار، همه کار صف‌اند؛ با سقف نرخ هر کانال و کل ربات؛ روی 429 تا `retry_after` صبر.
- **هیچ مسیر حذفی در کد نیست (قانون ۶):** یک تست CI کل `panel/` را میگردد و اگر `deleteMessage` یا `delete_message` در کد بود، شکست میخورد. علاوه بر آن، پنل در شروع با `getChatMember` دسترسی خود ربات را میخواند؛ اگر ربات اجازه‌ی حذف داشت، به مالک هشدار میدهد که آن را بردارد.
- **ورود به داشبورد (قانون ۱۰):** دکمه‌ی «لینک ورود» ← ربات یک لینک ۵دقیقه‌ای یک‌بارمصرف به چت خصوصی مالک میفرستد ← کوکی جلسه. بی رمز، بی ترمینال.

### ۳.۷ استقرار بی ترمینال (GitOps)
- روی سرور پنل یک `deployer` (systemd timer، هر ۲ دقیقه) شاخه‌ی `main` را میخواند. اگر commit تازه بود: build، `alembic upgrade`، `up -d`، بررسی `/healthz`. اگر سالم نشد، **به commit قبلی برمیگردد** و هشدار میدهد.
- پس مسیر هر تغییر: Claude روی شاخه کار میکند ← PR ← مالک میبیند و merge میکند ← پنل خودش به‌روز میشود. مالک نه SSH میخواهد نه ترمینال.
- اگر ریپو خصوصی است: پنل یک **deploy key فقط‌خواندنی** میسازد و صفحه‌ی راه‌اندازی آن را با یک دکمه‌ی کپی و لینک مستقیم صفحه‌ی Deploy keys گیت‌هاب نشان میدهد.

**هزینه‌ی چرخش IP (حساب‌شده از قیمت‌های بالا):**
- **node تازه:** هتزنر ساعتی حساب میکند و سقفش قیمت ماه است. node که کل ماه روشن بماند ۶٫۴۹ میشود. ولی اگر nodeها مدام عوض شوند، هر جایگاه به نرخ ساعتی نزدیک میشود: ۰٫۰۱۰۴ × ۷۳۰ ساعت = حدود **۷٫۵۹**، یعنی حدود **۱۷٪ گران‌تر**.
- **عوض کردن Primary IP روی همان سرور:** سرور و سقف ماهانه‌اش سر جایشان میمانند. IP تازه ساعتی ۰٫۰۰۰۸ یورو است. بهایش یک خاموش و روشن شدن کوتاه است (H4).
- **نتیجه:** راه Primary IP احتمالاً ارزان‌تر است. M4.3 زمان واقعی قطعی و هزینه‌ی هر دو راه را میسنجد و بعد تصمیم گرفته میشود.

> **عددها ثابت نیستند:** هتزنر در ۲۰۲۶ دو بار قیمت را بالا برده و نوع‌های ارزان فعلاً موجود نیستند. برای همین کد قیمت را زنده از API میخواند و سقف بودجه همیشه با قیمت روز سنجیده میشود.
