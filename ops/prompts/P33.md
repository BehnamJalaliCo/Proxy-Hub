# پرامپت ۳۳: وارسی خودکار اسپانسر در ‎@MTProxybot‎ (پس از PR ۴۴، D63)

> مالک این را میچسباند: «`git pull` بزن (روی `main`)، بعد فایل `ops/prompts/P33.md` را بخوان و تا رسیدن به نتیجه، خودت اجرا کن.»

قاعده‌های `ops/prompts/README.md` برقرار است:
- فارسی و **کوتاه** با مالک.
- هیچ uuid، کلید، tag، لینک کامل یا IP کامل در گزارش نیاید. نشانی پروکسی را فقط با نام جایگاهش (مثل `slot3`) یا ۲ بخش آخر IP بنویس.
- commit یا push نکن.

فرمان‌ها:
- `Q() { sudo docker compose -p proxyhub exec -T postgres psql -U proxyhub -d proxyhub -At -c "$1"; }`
- `C2="sudo docker compose -p proxyhub exec -T api python -m proxyhub.sponsor"`

**این پرامپت چیزی را عوض نمیکند و هیچ دکمه‌ای نمیزند.** `inventory` را هم خودت شروع نکن؛ پنل باید خودش شروع کند.

**چرا:**
- صفحه‌ی «اسپانسر» برای slot1 و slot2 «اسپانسر نشان داده نمیشود» و برای دو پروکسی دیگر «خوانده نشده» میگفت.
- آخرین خواندن ۱۱-۰۷ بود، پیش از PR ۳۲ که عنوان کانال را در صفحه‌ی ربات میفهمد. پنل فقط با دکمه یا CLI میخواند.

**چه عوض شد (PR ۴۴):**
- پنل خودش `inventory` را در صف میگذارد (actor `sponsor:auto`): روزی یک بار، و ۱۰ دقیقه پس از هر تنظیم اسپانسر. حداکثر یک کار در ساعت.
- اگر صفحه‌ی یک پروکسی فعال اسپانسر ‎@ipoxxo‎ را نشان ندهد، پنل اسپانسرش را دوباره تنظیم میکند (`sponsor.promotion_repair`)، برای هر پروکسی حداکثر روزی یک بار.
- اگر خواندن بعدی باز هم درست نبود، مالک یک هشدار در تلگرام میگیرد (`sponsor.promotion_alert`).
- مهاجرتی ندارد.

0. **پیش‌شرط:**
   - `deploy_status.sh` باید `RESULT: up to date` بدهد.
   - `Q "SELECT version_num FROM alembic_version"` باید `0033_reality_traffic` بدهد.
   - شمار خطای worker باید ۰ باشد.
1. **وارسی اول** (هر ۳ دقیقه بسنج، حداکثر ۳۰ دقیقه پس از استقرار):
   - `Q "SELECT at, actor, action, reasons->'reasons', reasons->'context'->>'channels' FROM actions_log WHERE action LIKE 'sponsor.mtproxybot%' AND at > now() - interval '2 hours' ORDER BY id DESC LIMIT 25"`.
   - انتظار، به ترتیب زمان:
     - `sponsor.mtproxybot_requested` با `["inventory", "look"]` و actor `sponsor:auto`؛
     - `sponsor.mtproxybot_list_read` با `complete`؛
     - یک `sponsor.mtproxybot_menu_read` برای هر پروکسی فعال (۴ تا)؛
     - `sponsor.mtproxybot_finished` با `done`.
   - اگر پس از ۳۰ دقیقه `requested` نیامد، بگو چرا: `$C2 status` (بخش `job`)، کلید توقف، حال حساب دوم، و `Q "SELECT state, state_reason, count(*) FROM mtproxy_registrations GROUP BY 1, 2"`.
2. **وضعیت تازه:** `$C2 status`. گزارش کن:
   - `checked_at`؛
   - `counts`: `live`، `promotion_ok`، `promotion_problem`، `promotion_unread`؛
   - برای هر پروکسی `live`: نام جایگاه، `promotion` و `menu_read_at`.
   - **اگر همه `ok` بودند، کار تمام است.** به گام ۵ برو.
3. **اگر `promotion_problem` بیش از ۰ بود:**
   - برای هر پروکسی مشکل‌دار، دلیل `menu_read` را بگو (`not_shown`، `several`، `title:…` یا نام کانال).
   - شکل صفحه‌ی همان پروکسی را از `screens` در خروجی `$C2 status` گزارش کن: متن و دکمه‌ها، **بی نشانی و بی tag**. Claude ریپو با آن میفهمد اسپانسر واقعاً نیست یا پنل صفحه را بد میخواند.
   - تا ۵ دقیقه بعد: `Q "SELECT at, actor, action, target IS NOT NULL, reasons->'reasons' FROM actions_log WHERE action IN ('sponsor.promotion_repair', 'sponsor.promotion_set', 'sponsor.flow_stuck', 'sponsor.flow_failed', 'sponsor.promotion_alert') AND at > now() - interval '3 hours' ORDER BY id DESC LIMIT 20"`.
   - انتظار: یک `sponsor.promotion_repair` برای هر پروکسی `not_shown` یا `other`، و چند دقیقه بعد `sponsor.promotion_set` برای همان‌ها.
4. **وارسی دوم** (فقط اگر گام ۳ ترمیمی داشت؛ حدود ۷۰ دقیقه پس از پایان وارسی اول، هر ۱۰ دقیقه بسنج، حداکثر ۹۰ دقیقه):
   - پنل باید خودش `inventory` دوم را شروع کند. گام ۱ و ۲ را دوباره گزارش کن.
   - اگر باز هم مشکل بود، باید یک `sponsor.promotion_alert` ثبت شده باشد و مالک پیامش را در تلگرام گرفته باشد. از مالک بپرس.
5. **گزارش پایانی** در یک بلوک کوتاه برای Claude ریپو: زمان‌ها، شمارها، وضعیت هر جایگاه، و اگر بود، شکل صفحه‌ها.

**نکن:**
- `inventory`، `cleanup` یا «ثبت دوباره» را خودت شروع نکن.
- هیچ چیزی را با دست در ‎@MTProxybot‎ نزن.
- تنظیمات را عوض نکن.
- `git push` نکن.
