# پرامپت ۲۴: اولین پست‌های ناظر (D52) و خبر فوری (D56)

> مالک این را میچسباند: «`git pull` بزن (روی `main`)، بعد فایل `ops/prompts/P24.md` را بخوان و تا رسیدن به نتیجه، خودت اجرا کن.»

قاعده‌های `ops/prompts/README.md` برقرار است:
- فارسی و **کوتاه** با مالک.
- هیچ رمز، کلید، متن کامل خبر یا لینک کامل پروکسی در گزارش نیاید.
- commit یا push نکن.

فرمان‌ها:
- `Q() { sudo docker compose -p proxyhub exec -T postgres psql -U proxyhub -d proxyhub -At -c "$1"; }`
- `W() { sudo docker compose -p proxyhub logs --since "$1" worker 2>&1 | grep -E "content|publisher|breaking" | tail -n 40; }`

**چه عوض شد (PR ۲۶):**
- **D56، خبر فوری:**
  - خبری که کمتر از ۳۰ دقیقه عمر دارد و **دست‌کم ۲ منبع جدا** آن را گفته‌اند، بیرون از نوبت به Claude میرود.
  - اگر Claude تأییدش کند و بگوید `breaking`، ارتقا پیدا میکند (`breaking_at`).
  - پست‌گذار آن را **فوراً** میفرستد، بیرون از برنامه‌ی روز و در ساعت‌های بی‌پست هم، با عنوان «🔴 فوری | …».
  - بودجه: حداکثر ۵ در ۲۴ ساعت، ۲۰ دقیقه فاصله بین دو خبر فوری، و ۵ دقیقه پس از هر پست.
  - جزو «پست در روز» حساب نمیشود.
  - پاسخ Claude یک کلید تازه دارد: `breaking`.
- سقف پیش‌فرض روزانه‌ی پل از ۴۰ به ۸۰ رفت. اگر مالک تنظیمات ناظر را قبلاً ذخیره کرده باشد، همان عدد ذخیره‌شده میماند.
- مهاجرت `0029_breaking_news`.

0. **پیش‌شرط:**
   - `deploy_status.sh` باید `RESULT: up to date` بدهد.
   - `Q "SELECT version_num FROM alembic_version"` باید `0029_breaking_news` بدهد.
   - شمار خطای worker باید ۰ باشد.
1. **تنظیمات** (فقط بخوان):
   - `Q "SELECT value->>'posts_per_day', value->>'main_enabled' FROM settings WHERE key='posting'"`.
   - `Q "SELECT value->>'mode', value->>'bridge_daily_cap', value->>'per_slot', value->>'breaking_enabled', value->>'breaking_per_day' FROM settings WHERE key='content.qc'"`. اگر ردیفی نبود، پیش‌فرض‌ها برقرارند: `auto`، ۸۰، ۳، روشن، ۵.
   - اگر `bridge_daily_cap` کمتر از ۸۰ بود، **از مالک بخواه** در داشبورد، صفحه‌ی صف بازبینی، «سقف روزانه‌ی اشتراک» را ۸۰ کند. با ۱۵ پست در روز، ۴۰ کم است.
2. **اولین تصمیم‌های ناظر** (تا نوبت بعدی پست، حداکثر ۲ ساعت):
   - `Q "SELECT qc_decision, decided_by, count(*) FROM content_candidates WHERE qc_at IS NOT NULL GROUP BY 1, 2"`.
   - `Q "SELECT backend, outcome, count(*) FROM content_qc_calls GROUP BY 1, 2"`.
   - `Q "SELECT s.ref, count(*) FILTER (WHERE c.qc_decision = 'approve'), count(*) FILTER (WHERE c.qc_decision = 'reject'), s.enabled, s.disabled_reason FROM content_sources s LEFT JOIN content_candidates c ON c.source_id = s.id AND c.qc_at IS NOT NULL GROUP BY s.id ORDER BY s.id"`.
   - انتظار: کانال‌های پروکسی (imtproto، mtpproxyirani، proxydaemi) بیشتر رد میشوند و ممکن است خودکار خاموش شوند. این درست است.
3. **پست ناظر در کانال آزمایشی:**
   - `Q "SELECT p.id, p.created_at, p.breaking, p.media_kind, c.decided_by FROM posts p LEFT JOIN content_candidates c ON c.id = p.content_candidate_id ORDER BY p.id DESC LIMIT 3"`. انتظار: پستی با `decided_by = qc`.
   - از مالک بخواه پست را روی آیفون ببیند: تیتر کوتاه فارسی، متن کوتاه، عکس یا ویدیو، و لینک‌ها زیر آن. بی نام منبع، بی @ و بی لینک بیگانه.
4. **خبر فوری** (فقط گزارش؛ چیزی را دستی نساز):
   - `Q "SELECT count(*) FILTER (WHERE qc_breaking), count(*) FILTER (WHERE breaking_at IS NOT NULL) FROM content_candidates"`.
   - `Q "SELECT id, created_at, plan_slot FROM posts WHERE breaking ORDER BY id DESC LIMIT 5"`.
   - `W 2h | grep -iE "breaking|Traceback"`.
   - اگر در این مدت خبر فوری‌ای رفت، از مالک بخواه نگاهش کند: «🔴 فوری | …» در بالا. اگر نرفت، عیبی ندارد؛ فقط گزارش کن.
5. **گزارش پایانی** در یک بلوک کوتاه برای Claude ریپو.

**نکن:**
- تنظیمات را خودت عوض نکن. سقف‌ها و رونمایی با مالک است.
- خبر یا نامزد را دستی تأیید یا ارتقا نده.
- `git push` نکن.
- `removal on` را نزن.
- به کانال اصلی دست نزن.
